# Заметки по изученным паттернам

Рабочий файл с примерами и объяснениями конкретных решений/паттернов Go, встретившихся при разработке этого проекта. Не для сдачи — личный конспект.

## Замыкание в `defer` захватывает переменную, а не её значение на момент объявления

Аргументы деферящегося вызова вычисляются сразу, в момент `defer`:
```go
x := 1
defer fmt.Println(x) // "1" зафиксировано здесь
x = 2
// при выходе из функции выведется: "1"
```

Замыкание (анонимная функция без аргументов) захватывает саму переменную по ссылке — читает её значение в момент фактического исполнения, то есть при выходе из функции:
```go
x := 1
defer func() { fmt.Println(x) }() // замыкание захватывает x
x = 2
// при выходе из функции выведется: "2"
```

### Применение: cleanup при частичном сбое инициализации

Комбинация «именованные возвраты + `defer` с замыканием» — рабочий способ закрыть уже открытые ресурсы, если один из последующих шагов инициализации упал:

```go
func New(ctx context.Context, logger *slog.Logger) (app *Application, err error) {
	app = &Application{logger: logger}
	defer func() {
		if err != nil {
			app.Close(ctx)
		}
	}()

	if err = app.setDatabase(...); err != nil {
		return nil, fmt.Errorf("set database: %w", err)
	}
	if err = app.setServer(...); err != nil { // если упадёт здесь — БД уже подключена
		return nil, fmt.Errorf("set server: %w", err)
	}

	return app, nil
}
```

Работает это благодаря именованным возвратам: `return nil, fmt.Errorf(...)` сначала присваивает значения именованным переменным `app`/`err`, и только потом выполняются отложенные функции — уже после присвоения, но до фактической передачи управления вызывающему коду. Поэтому замыкание в `defer` видит финальное значение `err`, а не то, что было на момент объявления `defer` (тогда `err` ещё `nil`).

Без именованных возвратов паттерн не сработал бы — замыканию было бы не на что закрываться.

Контекст: обсуждали применительно к [internal/app/app.go](internal/app/app.go) — `Close()` уже закрывает `httpServer` и `postgres`, но если `setServer` упадёт после успешного `setDatabase`, открытый пул к БД сейчас утекает, пока не внедрён этот cleanup.
